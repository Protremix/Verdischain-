## Что выяснил про устройство цепи

### Валидаторами управляет `pallet_dpos`, а не Staking

```
Staking pallet storage keys : 0     ← скомпилирован, но НЕ используется
Dpos    pallet storage keys : 54    ← реально управляет сетом
Session pallet storage keys : 68
Grandpa pallet storage keys : 87
```

**`Dpos.Validators` — это MAP с 21 записью, а не зашитый в genesis список.** Это принципиально: членство хранится как состояние по каждому аккаунту, а значит теоретически изменяемо.

### В рантайме ЕСТЬ вызов регистрации

Найдено в метаданных:
```
register_validator   ← вот это главное
bond, unbond, stake, unstake
validate, delegate, undelegate
activate, deactivate, set_commission
withdraw_unbonded
```

То есть **архитектурно новый валидатор может зарегистрироваться сам** — без governance, без Council, без потерянных ключей.

### Как выглядит запись валидатора

```
account   32 байта
stake     1,000,000 VRDX (15 нод) или 10,000,000 VRDX (6 нод)
статус    "Unknown"
Dpos.TotalStaked = 75,000,000 VRDX  (0.07% от эмиссии)
```

## Почему это всё-таки не работает

Проверил 33 аккаунта мейннета и наши ключи. Результат:

### 1. Наши acco-ключи — НЕ стейкающие аккаунты

```
V18, V19, DE, V15, V16, V17, NL, V9, V10, V20, CB
→ все 11: NOT ON CHAIN, никогда не получали средств
пересечение с Dpos.Validators: 0
```

21 стейкающий аккаунт — **отдельный набор ключей**, которого у нас нет. Наши keystore содержат только session-ключи (`acco`/`babe`/`gran`) для подписи блоков, а не stash-аккаунты, владеющие стейком.

### 2. Все 99.9 млрд VRDX — на pallet-аккаунтах без приватных ключей

Расшифровал top-6 держателей:
```
modlverdisec   25,000,000,000 VRDX
modlverdist0   20,000,000,000 VRDX
modlverdisdp   20,000,000,000 VRDX
modlverdisdx   10,000,000,000 VRDX
modlverdisdv   10,000,000,000 VRDX
modlverdiscm    5,000,000,000 VRDX
               ──────────────
               90,000,000,000 VRDX
```

Префикс `modl` = **PalletId-аккаунт**. У таких аккаунтов приватного ключа не существует физически — они принадлежат паллетам (treasury, vesting, presale, DEX) и расходуются только через логику паллета, то есть через governance.

### 3. Governance закрыт

```
Sudo pallet          : отсутствует
Council              : 3 члена
приватных ключей     : 0 из 3 (проверено на всех серверах)
```

### Замкнутый круг

```
чтобы добавить валидатора → нужен стейк ≥ 1,000,000 VRDX
чтобы получить стейк       → нужен аккаунт с балансом
все балансы                → на pallet-аккаунтах без ключей
разблокировать pallet      → нужен Council
ключей Council             → нет
```

**Итог: добавить 22-го валидатора нельзя. Уменьшить сет до 15 — тоже нельзя.**

## Что это значит на практике

### Мейннет работает и будет работать
```
best=47997 finalized=47988 lag=9 peers=15
21 авторитет, 15 работают, порог 15
финализирует 10 блоков/мин = темп производства
```
Пока все 15 нод живы — цепь здорова. Серверы оплачены, сервисы в автозапуске, мониторинг стучит в Telegram каждые 30 минут.

### Единственный риск — падение одной ноды

Если умрёт одна нода: 14 из 15 → **финализация встаёт**. Блоки продолжат производиться, но не финализируются.

**Это восстановимо.** Поднимаем ноду обратно → финализация догоняет. Именно так я утром починил тестнет: поднял остановленные ноды, и финализация пошла с #109338 дальше.

Опасность не в самом сбое, а в том, чтобы **не заметить его вовремя**. Тестнет стоял 5 суток именно поэтому. Теперь мониторинг присылает CRIT сразу.

### Чего НЕ произойдёт
- Деньги не пропадут — балансы в состоянии цепи, оно на 15 archive-нодах + 3 бэкапа
- Цепь не «сломается» — genesis, история, балансы целы
- Аудит не станет невозможным — это архитектурное замечание, не уязвимость

## Что реально можно сделать без ключей

### 1. Минимизировать риск падения — уже сделано частично
- ✅ Все юниты `enabled` — переживут перезагрузку
- ✅ Бэкап 15 keystore с проверенными хешами
- ✅ Мониторинг с CRIT в Telegram
- ✅ Резервные bootnodes (3 вместо 1)
- ✅ Журналы ограничены — ENOSPC больше не убьёт ноду

### 2. Что предлагаю добавить
- **Автоперезапуск при отставании финализации** — watchdog на каждом хосте: если нода отстала или упала, поднять её без моего участия
- **Второй бэкап keystore в другое место** (сейчас все три архива на одном рабочем ноутбуке)
- **Мониторинг чаще** — 30 минут это долго при нулевом запасе; можно 5

### 3. Долгосрочно — это решается только новым генезисом

Честно: **чтобы получить нормальный запас авторитетов, нужна новая цепь.** Мейннету 3–7 суток, 33 аккаунта, реальных пользователей нет. Цена перезапуска сейчас минимальна, а через год будет невозможна.

При новом генезисе:
- authority set = столько, сколько ключей реально контролируешь (15 → порог 11, запас 4)
- Sudo-ключ сохранён для аварийного управления
- stash-ключи задокументированы и забэкапены
- ключи Council у тебя

**Это твоё решение, не моё.** Я не буду делать re-genesis без явного согласия — это стирание цепи.

## Ответ на вопрос одной фразой

Если ключей на USB нет — мейннет продолжает работать, но остаётся хрупким: любая упавшая нода останавливает финализацию до её подъёма. Это не потеря денег и не поломка цепи, а операционный риск, который закрывается мониторингом и автоперезапуском. Полностью убрать его можно только новым генезисом — и сейчас это дешевле, чем когда-либо потом.
